Steno — Specification vs. Implementation Review

Date: 2026-08-23  ·  Specs: openspec/specs/model-provisioning/spec.md, openspec/specs/capture-key-interception/spec.md  ·  Code: crates/steno-daemon, crates/steno-cosmic  ·  HEAD: 8313ca4  ·  Design intent: capture key Ctrl+Super and the flat tdt model layout are deliberate decisions (owner-confirmed 2026-08-23) — the specs predate them and are stale.
Verdict: the specs describe a design that no longer exists — on purpose. The two largest spec/implementation deltas are intentional: the capture key is now Ctrl+Super (no Space) because the spec's Ctrl+Super+Space approach did not work in practice, and the model file set is the 7-file tdt/ set from altunenes/parakeet-rs — verified to be exactly what the HuggingFace repo contains and what the ParakeetTDT model loads (4 of the 7 files are on disk with byte-exact repo sizes, flat in ~/.config/steno/models/parakeet, owner-confirmed working). The specs, not the code, need updating. Two genuine bugs remain in the current tree: (1) listen() panics on the first idle tick (listener.rs:44, proven — §3.3), which a successful end-to-end capture test on this exact tree rules out, so it most likely entered with the final edit; and (2) the model-provisioning layout is inconsistent — is_model_available() probes models/tdt/… (owner-confirmed invalid) and hf-hub writes to parakeet/tdt/…, while the layout the model consumes is flat parakeet/… — so every startup re-enters the download branch, and a fresh machine would provision a layout the model does not read.

2.1 model-provisioning — implementation: crates/steno-daemon/src/model.rs

Requirement (spec)StatusFindings
Model directory location — files in ~/.config/steno/models/parakeet; fixed, not changeable by config or environment VIOLATED
  • Directory is derived from $XDG_CONFIG_HOME → $HOME → /tmp fallback (model.rs:48-55, fallback at line 50). A /tmp model dir is world-readable and contradicts both the spec's "fixed, user-writable location" wording and the architecture quality goal that model/audio data be accessible only to the logged-in user. The spec wording vs. XDG derivation is a deliberate conflict to resolve (§5.1); the /tmp fallback should become a hard error either way.
  • On-disk layout is flat in parakeet/ (verified, §1) — the layout the ParakeetTDT model consumes (owner-confirmed). But the current code's download destination is parakeet/tdt/… (hf-hub joins filename into local_dir) — a mismatch that matters on fresh machines (§2.1, "Missing files" row).
Missing files trigger a download — absent files are downloaded from altunenes/parakeet-rs into the model dir; present files are not re-downloaded VIOLATED
  • The availability check is invalid (owner-confirmed: "it needs to strip the tdt/ path"). is_model_available computes the probe path with local_dir.with_file_name(file) (model.rs:62). Because file carries a tdt/ prefix, with_file_name replaces the final parakeet segment and probes ~/.config/steno/models/tdt/<name> — which matches neither the flat on-disk layout nor the code's own download destination parakeet/tdt/<name>. The check can therefore never return true; every startup enters the download branch.
  • Because hf-hub's local-dir path has no existence check (verified in its source, §1), a fresh machine downloads the full set every startup until the check is fixed — ~3.3 GB including the two int8 variants.
  • Layout coupling: the tdt/ prefix is required in the download URL (the repo stores the files under tdt/ — verified) but must be stripped from the local path (both the probe and the write destination) so files land flat in parakeet/<basename>, where the model reads them. hf-hub couples URL and local name in the single filename argument, so the code must handle the split (e.g. download to parakeet/tdt/ and move to flat, or download per-file to a basename destination).
  • Presence check is exists() only — no non-empty/size component, so a zero-byte file counts as provisioned (M4).
Correct files are fetched — exactly config.json, decoder_joint.onnx, encoder.onnx, encoder.onnx.data, tokenizer.model; nothing else SPEC STALE (intentional)

The code's 7-file tdt/ set (model.rs:9-16) is the correct set: the repo's tdt/ directory contains exactly these 7 files (verified via the HF API), the 4 files on disk match their repo sizes byte-for-byte, and the owner confirms this is what the ParakeetTDT model loads. The spec's 5-file list names files that do not exist anywhere in the repo — the spec describes the old, non-working design.

Open question: 3 of the 7 files are absent from disk (decoder_joint-model.int8.onnx 18 MB, encoder-model.int8.onnx 652 MB, nemo128.onnx 139 KB), while the 4 non-int8 files constitute the confirmed-working set. If ParakeetTDT only needs those 4, drop the rest from REQUIRED_FILES — that removes ~670 MB of startup download. Confirm before changing.
Integrity is verified — corrupt/truncated/tampered downloads rejected; a failed model must not be reported ready VIOLATED
  • No size check, no content hash, no temp-file-then-rename. Files are written directly to their destination by hf-hub's send() (model.rs:70-92).
  • An interrupted download leaves a partial file that a later startup accepts (the availability check has no size/non-empty component — and currently never passes anyway).
  • Expected sizes are now trivially pinable: the HF API reports exact byte counts for all 7 files (table in §7), so EXPECTED_SIZES constants + post-download byte-count verification is a small, well-specified fix.
Provisioning occurs during startup — before the transcription model is loaded VACUOUS Ordering is correct (main.rs:37, before the listener is spawned), but parakeet_rs is not a daemon dependency and the daemon itself loads no model — transcription currently happens outside the daemon (the owner runs the ParakeetTDT model against the provisioned directory). The "provisioning precedes transcription" scenario holds only because the daemon's transcription step does not exist yet.
Provisioning errors are reported — failure reported, no false "ready" PARTIAL Transport errors propagate via ? in main.rs:37 and exit non-zero. But because integrity failures are never detected (see above), a corrupt or truncated download is reported as success — the spec's core scenario ("download is corrupted ⇒ not ready") is unmet.

2.2 capture-key-interception — implementation: crates/steno-daemon/src/listener.rs

Requirement (spec)StatusFindings
Capture key definition — Ctrl+Super+Space pressed simultaneously; Space is the base key; modifiers-only must NOT be active SPEC STALE (intentional)
  • Deliberate design change (owner-confirmed): the capture key is now Ctrl+Super with no base key. The spec's Ctrl+Super+Space approach (registered hotkey + is_key_pressed(SPACE) check, as in the deleted capture_key.rs) was tried and "couldn't get it work" on the target desktop; the current polling implementation was written this morning and tested successfully by the owner. main.rs:39-40 documents the intent in-code ("grab Ctrl+Super to trigger the recording").
  • The spec's "Only modifiers held (no base key) ⇒ NOT active" scenario is deliberately voided: with no base key, both modifiers held is the active state, and a single modifier alone is not active — which the current handle_modifiers predicate (listener.rs:57) implements correctly for the new design.
  • Action: update the spec and the archived design doc to Ctrl+Super; do not "restore" the Space check.
Capture key press detection — inactive→active transition; including press while modifiers were already held VIOLATED

Dead-on-arrival bug in the current tree: the poll loop panics on the first idle tick. handle_modifiers returns Option::None whenever no transition occurred — the normal case on every tick where a capture transition is not in flight — and the loop does .map(…).unwrap().await? (listener.rs:39-44). None.map(f).unwrap() panics, so the task dies on its very first tick (no keys are held at startup). Empirically verified: a spawned listen() panics at listener.rs:44 within ~0.4 s (called `Option::unwrap()` on a `None` value). While this line exists, the capture key cannot produce any events and no successful end-to-end capture test of this exact tree is possible — so the owner's successful test almost certainly ran on an earlier iteration of this morning's work (listener.rs was edited minutes before this review). The fix is one line: send/await only when Some; an idle tick is a no-op. Re-verify the Ctrl+Super flow end-to-end after the fix.

Beyond the panic: for the new Ctrl+Super definition, the is_active transition logic in the 15 ms poll loop (listener.rs:34-53) is actually correct — it handles press while modifiers were already held, and the event-loop design is a reasonable realization of the design doc's poll approach. The panic is the blocker, not the state machine.
Capture key release detection — release as soon as any of the capture keys is dropped PARTIAL
  • Under the intentional Ctrl+Super definition, release means dropping either modifier — and handle_modifiers does exactly that (both held && is_active → Stop; either dropped → Stop). The old concern ("releasing Space alone leaves capture stuck active") is void: Space is no longer part of the key.
  • Blocked in practice by the idle-tick panic above — no transition is ever observed until listener.rs:44 is fixed.
Capture key event logging — distinct press and release log entries, per cycle, in order, so an operator can verify interception PARTIAL
  • The capture-key layer logs nothing on press/release. The operator-visible signal is one layer down: Start recording / Stop recording from the Recorder (recorder.rs:41, recorder.rs:46) — these fire on exactly the same transitions and are what an operator (and the owner, in the successful test) actually observes.
  • If the recorder-level lines satisfy the spec's intent ("operator can verify interception"), the spec wording should be amended; otherwise add capture_key: pressed / capture_key: released entries in handle_modifiers. No test currently asserts any logging behavior.

3.3 Against the architecture (beyond the two specs, the next layer of "important missing")

  • Audio capture: no PipeWire integration exists. Recorder is a boolean flag — it records nothing. (Explicitly out of scope for the two archived specs, but it is the reason the Start/Stop commands go nowhere.)
  • Transcription: parakeet_rs is not a dependency; the daemon loads no model. The ParakeetTDT model is currently exercised externally against the provisioned directory. The daemon's "provisioning before the model is loaded" is nominal until parakeet_rs lands here.
  • Text injection: no /dev/uinput integration.
  • Notifications: no D-Bus broadcast; steno-cosmic is a Hello, world! stub.
  • Docs: README "Getting started" is a TODO; architecture docs 06–11 are near-empty placeholders.

3.4 Robustness gaps in the current daemon wiring

  • [P0] Dead-on-arrival panic in listen() (B1). See §3.2. Note the tension: the owner reports a successful capture test this morning — impossible against this exact tree (the task is dead before any key is pressed), so the panic almost certainly entered with the final edit. Fix, then re-test.
  • Failed listener is invisible. tracker.spawn(listener.listen(…)) (main.rs:41) drops the task's Result — and tokio converts the panic above into a JoinError that is likewise dropped. Nothing is logged; the daemon proceeds to wait for a shutdown signal while its only capture path is dead. The same silent-death path applies if active_modifiers() starts erroring later (device hotplug, permissions). There is no supervision, no error surfacing, no non-zero exit.
  • Grab mode — reconcile, don't assume. The manager is built with .grab() (listener.rs:20). The archived design doc says the final form must not grab because an earlier grab form "exclusively captured every input node, which broke the user's session." But the current .grab() build was tested successfully on the desktop this morning — kbd-global's grab may behave differently from what broke the session. Decide explicitly and make doc and code agree.
  • OS-coupled unit tests. The three listener tests construct a real HotkeyManager (evdev backend, grab mode) via KeyListener::new(). The design doc's decision to isolate the key source behind a trait (a KeyEventSource) was never realized — the state machine is only testable on a machine with evdev access, which makes CI environment-dependent.
  • expect() in main.rs:14 (install SIGTERM handler) panics instead of returning an error.

5. Spec/design inconsistencies to resolve

Before (or while) fixing the code, these contradictions should be settled deliberately — otherwise a fix will violate one document or the other:

  1. Fixed path vs. $XDG_CONFIG_HOME. The spec says the model dir "MUST NOT be changed by configuration or environment"; the archived design decision says to derive it from the user's config dir honouring $XDG_CONFIG_HOME. Both the old and new code honour the env var. Recommendation: keep XDG derivation (platform convention, design's explicit choice), amend the spec wording, and remove the /tmp fallback (fail instead).
  2. Which files, where in the repo — now resolved by evidence. Repo-verified: the 7 tdt/ files exist under tdt/; the spec's 5 files exist nowhere in the repo. Disk-verified: the 4 non-int8 files sit flat in parakeet/ with byte-exact repo sizes and work with ParakeetTDT (owner-confirmed). Action: the spec adopts the tdt/ set with a flat local layout; then decide whether the 3 int8/nemo128 files are needed (S2). Note for the spec: the tdt/ prefix belongs in the download URL only — local paths are flat — because hf-hub joins filename into local_dir (B2).
  3. "Known, expected content" vs. size. The spec says verify against "known, expected content"; the design decision was "size + optional hash" and the deleted code implemented size only. Size catches truncation but not content tampering. Recommendation: implement size now (all 7 sizes are known from the repo API — §7), add SHA-256 constants as a follow-up, and note the strength in the spec.
  4. Grab mode. Design doc says the final form must not grab (an earlier grab form broke the session); current code calls .grab() and was tested successfully on the desktop this morning. Decide explicitly which story is true — if kbd-global's grab is safe, update the design doc; if not, remove .grab(). Don't leave doc and code silently disagreeing.
